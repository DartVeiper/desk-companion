# Desk Companion — план проекта (v2, всё на одном Raspberry Pi)

Один физический блок на столе: Raspberry Pi Zero 2 W напрямую читает датчики, рисует экран, крутит брокер и базу. Один провод питания, одна коробка. Плюс фоновый агент на игровом ПК (когда он включён) и приложение для истории.

---

## 1. Общая архитектура

```
┌─────────────────────────────────────────────┐
│        ФИЗИЧЕСКИЙ БЛОК (стол) — один Pi        │
│                                                │
│  Raspberry Pi Zero 2 W                        │
│   ├── UART  ── LD2410 (радар)                 │
│   ├── I2C   ── SCD41 (CO2/темп/влажность)      │
│   ├── SPI   ── TFT-экран (ILI9341)            │
│   ├── GPIO  ── Энкодер с кнопкой               │
│   ├── Mosquitto (MQTT-брокер, локально)        │
│   ├── SQLite (база данных, постоянно)          │
│   ├── Python-сервис отрисовки экрана (luma.lcd)│
│   └── WiFi (встроен, 2.4 ГГц) ── интернет      │
│         (NTP, погода) + домашняя сеть          │
└──────────────────┬─────────────────────────────┘
                    │  WiFi / MQTT
        ┌───────────┴────────────┐
        ▼                        ▼
┌──────────────────┐     ┌──────────────────┐
│  ПК-агент (Python) │     │  Приложение      │
│  работает только    │     │  (веб или .NET)  │
│  пока игровой ПК     │     │  online-статус,  │
│  включён:            │     │  день/неделя,    │
│  ├─ pynput           │◄────┤  графики —       │
│  ├─ pywin32+psutil   │     │  все данные      │
│  ├─ pycaw            │     │  берёт из базы   │
│  ├─ LibreHardwareMon │     │  на Pi           │
│  └─ шлёт всё на Pi ──┘     └──────────────────┘
└──────────────────┘
```

**Принцип:** всё, что не требует данных с ПК (часы, погода, presence, CO2), работает на Pi полностью самостоятельно. Экран — просто "витрина" общего состояния, переключение режима ничего не включает и не выключает в фоне. Pi — единственное место, где живут брокер и база, поэтому статус "устройство онлайн" в приложении честный и не зависит от того, включён ли игровой ПК.

**Что реально изменилось по сравнению с версией на ESP32:**
- Нет отдельного второго устройства и второго провода питания
- Нет PSRAM-головной боли с гифками — у Pi полноценная ОС и нормальная память
- Нет конфликта GPIO из-за Octal PSRAM (это была проблема конкретно ESP32-S3, у Pi её нет)
- Прошивка на C++/LVGL заменяется на обычный Python-скрипт — тот же язык, что и в остальном проекте
- Минус: после отключения питания Pi грузится 15-30 секунд (у ESP32 было почти мгновенно) — часы оживают не сразу
- Минус поменьше: изнашивание microSD от частой записи — не критично при записи агрегатами раз в минуту (см. п.4), но раз в год-два карту стоит быть готовым поменять

## 3. Данные и кто их поставляет

| Поле состояния | Источник | Обновляется |
|---|---|---|
| `presence` (за столом да/нет) | LD2410 → Pi (напрямую, UART) | реального времени |
| `co2`, `temperature`, `humidity` | SCD41 → Pi (напрямую, I2C) | раз в 5–10 сек |
| `weather` | Pi сам стучится в open weather API | раз в 10–15 мин |
| `active_app`, `category` (код/игра/браузер) | ПК-агент → MQTT (на Pi) | при смене окна |
| `keystrokes_count`, `mouse_clicks` | ПК-агент (pynput) → MQTT | раз в минуту (агрегат, не по событию!) |
| `audio_active` | ПК-агент (pycaw, пик на выходе) → MQTT | раз в секунду |
| `afk_by_input` (по бездействию клавы/мыши) | ПК-агент → MQTT | реального времени |
| `manual_status` | Энкодер на блоке → Pi (напрямую, GPIO) | по нажатию, авто-сброс через 4–6 ч |
| `gpu_temp`, `gpu_load`, `cpu_temp`, `cpu_load` | ПК-агент (LibreHardwareMonitor) → MQTT | раз в 2–3 сек |
| `anomaly_flag`, `anomaly_reason` | ПК-агент (IsolationForest поверх activity_minute) → MQTT | раз в час или по событию |
| `rain_soon_minutes` | Pi сам стучится в API Яндекс.Погоды (nowcast) | раз в 5–10 мин |
| `streak_days` | Pi считает сам поверх `activity_minute` (перерыв в каждом 2-часовом окне) | раз в сутки |

## 4. Схема базы данных (SQLite, живёт прямо на Pi)

Важно: **не пишем каждое нажатие клавиши отдельной строкой** — это утопит базу и лишний раз изнашивает microSD. Пишем агрегаты.

```sql
-- События смены состояния (мало записей, только на изменение)
CREATE TABLE state_events (
    id INTEGER PRIMARY KEY,
    ts DATETIME,
    presence BOOLEAN,
    active_app TEXT,
    category TEXT,          -- code / game / browser / other
    audio_active BOOLEAN,
    manual_status TEXT      -- NULL если не задан вручную
);

-- Поминутные агрегаты активности (компактно, ~1440 строк/день)
CREATE TABLE activity_minute (
    ts DATETIME PRIMARY KEY,
    keystrokes INTEGER,
    mouse_clicks INTEGER,
    mouse_distance_px INTEGER,
    at_desk BOOLEAN,
    category TEXT
);

-- Показания воздуха (раз в 5-10 мин достаточно, не каждую секунду)
CREATE TABLE env_readings (
    ts DATETIME PRIMARY KEY,
    co2 INTEGER,
    temperature REAL,
    humidity REAL
);
```

Если позже упрёшься в объём данных или захочешь удобные запросы "по времени" — миграция на **InfluxDB** делается безболезненно (тоже можно прямо на Pi), схема выше уже готова к этому переходу.

## 5. MQTT-топики (контракт между Pi и ПК-агентом)

Брокер локальный (на самом Pi), но топики оставляем как единый контракт — так проще отлаживать (`mosquitto_sub` показывает любое сообщение независимо от того, кто его слушает) и переносимо, если архитектура ещё раз поменяется.

```
home/desk/presence          → "1" / "0"                (Pi публикует сам себе/локально)
home/desk/env               → {"co2":650,"temp":23.4}  (Pi публикует)
home/desk/weather           → {"temp":18,"cond":"..."} (Pi публикует)
home/desk/manual_status     → "sleeping" / "" / ...    (Pi публикует при вводе с энкодера)

home/pc/active_app          → {"app":"rider64.exe","category":"code"}  (ПК публикует)
home/pc/activity_1min       → {"keys":142,"clicks":38,"mouse_px":8420}  (ПК публикует)
home/pc/audio               → "1" / "0"                (ПК публикует)
home/pc/heartbeat           → timestamp, раз в 30 сек   (ПК публикует)

home/pc/hardware            → {"gpu_temp":68,"gpu_load":92,"cpu_temp":54,"cpu_load":31}  (ПК публикует, LibreHardwareMonitor)
home/pc/anomaly             → {"flag":true,"reason":"session > 5h without break"}  (ПК публикует, ML-модель)
```

`home/pc/heartbeat` обязателен — без него при обрыве WiFi/зависании ПК-агента Pi молча "думает", что всё по-старому.

**Технический нюанс: retain-флаг.** Топики состояния стоит публиковать с флагом `retain=true` — тогда экран сразу получает последнее известное значение после перезапуска Python-сервиса на Pi, а не показывает пустоту.

## 6. Нюансы, которые надо решить ДО пайки

**WiFi у Pi Zero 2 W — только 2.4 ГГц, без 5 ГГц.**
Это нормально для большинства домашних роутеров (они держат обе полосы), но если роутер настроен только на 5 ГГц без отдельной сети 2.4 ГГц — Pi физически не подключится. Проверить заранее, что на роутере есть сеть 2.4 ГГц.

**Время загрузки Pi после сбоя питания.**
15-30 секунд от включения до готовности (в отличие от почти мгновенного старта ESP32) — если в квартире часто "моргает" свет, часы будут не всегда актуальны в первые секунды после каждого моргания. Не критично, но не "мгновенно", как было бы с ESP32.

**Износ microSD-карты.**
Частая запись сокращает жизнь карты. При записи агрегатами (раз в минуту, не по каждому событию) — это не проблема на годы вперёд, но стоит держать в голове, что через пару лет карту может понадобиться заменить, и не хранить единственную копию данных только на ней (см. нюанс про бэкап ниже).

**Бэкап базы данных.**
Раз данные теперь живут только на одной microSD в одном устройстве — стоит настроить простой периодический бэкап файла SQLite куда-то ещё (хоть на тот же игровой ПК по расписанию), иначе при порче карты пропадёт вся история разом.

**Вентиляция корпуса.**
SCD41 меряет воздух внутри коробки, а не в комнате, если корпус герметичный. Обязательно вентиляционные прорези рядом с датчиком при печати.

**Ложные срабатывания радара.**
LD2410 может путать вентилятор ПК/колебания штор с человеком. Заложи время на калибровку порогов после сборки — это нормально, не брак.

**Часовой пояс и переход на летнее/зимнее время.**
Не забыть смещение при выводе времени на экран и в приложении, иначе "недельный отчёт" будет путать дни.

**Приватность, если за компом не только ты.**
Трекер клавиатуры/окна/звука логирует всех, кто садится за твой ПК, не только тебя. Учти это как факт архитектуры, не как проблему.

**Автосброс ручного режима.**
Без таймера возврата в авто — легко забыть, что стоит "занят/не беспокоить" неделю назад.

**Определение конкретной игры (не просто "game"), а по имени.**
Steam хранит локальные логи/registry с последней запущенной игрой — можно вытащить точное название, а не только категорию.

**Питание — отдельным адаптером, не от игрового ПК.**
Даже несмотря на то, что теперь всего одно устройство — важно питать его от настенного адаптера, а не от USB-порта компьютера, иначе при выключении/сне ПК блок будет гаснуть вместе с ним, что убивает саму идею "часов на столе".

**LibreHardwareMonitor требует повышенных прав.**
Доступ к реальным датчикам температуры на Windows обычно требует запуска от администратора. Если ПК-агент настроен на автозапуск через Планировщик заданий — задачу нужно явно настроить на запуск "с наивысшими правами", иначе Режим 5 будет пустым без явной ошибки.

**Самокалибровка SCD41 (ASC).**
Датчик по умолчанию сам подстраивает ноль CO2, предполагая, что раз в несколько дней видит "свежий уличный воздух". Если блок постоянно стоит в помещении, которое редко проветривается до уличного уровня, показания могут медленно "уезжать" — не баг, можно отключить ASC программно.

**Зазор в корпусе под радиатор.**
Радиатор добавляет ~5-10 мм высоты над платой Pi. При проектировании 3D-печатного корпуса заложить это расстояние между платой и крышкой заранее, иначе радиатор упрётся в крышку.

**API Яндекс.Погоды для nowcast — нужна отдельная регистрация.**
Полный API исторически платный для бизнеса, но с 2026 года есть бесплатный тариф специально под проекты умного дома — под него нужно получить свой ключ отдельно (не тот же, что для обычного погодного прогноза, если используется другой провайдер). Сделать это заранее, до момента, когда дойдём до соответствующего шага в порядке работ.

## 7. Приложение для просмотра истории — выбор пути

**Вариант А — локальный веб-дашборд**
Маленький backend (Python/FastAPI прямо на Pi или отдельно), фронт — React/Tailwind с графиками. Открывается в браузере с телефона в домашней сети.

**Вариант B — нативное приложение на .NET MAUI**
Кроссплатформенное приложение (Android + Windows) из одной кодовой базы, читает ту же SQLite/API напрямую.

**Рекомендация:** начать с варианта А (веб) — быстрее даёт результат, можно обернуть в PWA позже.

Экраны приложения (день/неделя):
- **Сегодня** — текущий статус крупно, CO2/темп, активность по часам полосой
- **Неделя** — суммарное время за столом по дням, разбивка код/игры/браузер, сравнение с прошлой неделей
- **Настройки** — пороги CO2, время автосброса ручного режима, часы "ночного" окна для эвристики сна

## 8. Порядок работ

1. Прошить Pi (Raspberry Pi OS Lite), поднять Mosquitto + пустую SQLite, проверить SSH-доступ и WiFi
2. Подключить TFT-экран к GPIO Pi, вывести статичный UI (библиотека `luma.lcd` или `Adafruit CircuitPython RGB Display`) с 7 заглушками-режимами
3. Энкодер на GPIO — переключение режимов, антидребезг
4. LD2410 (UART) → Режим 3 ("меня нет") оживает реальными данными
5. SCD41 (I2C) → CO2/погода на Режим 1, NTP для времени
6. ПК-агент: pynput + pywin32/psutil + pycaw → публикация в MQTT на Pi, запись в SQLite
7. Связать всё через общую структуру состояния
8. Ручной режим (Режим 4) + автосброс
9. LibreHardwareMonitor → Режим 5 (GPU/CPU)
10. **Собрать 1-2 недели данных в `activity_minute`**, прежде чем включать Режим 6
11. Обучить и подключить IsolationForest → Режим 6
12. Настроить простой периодический бэкап SQLite (см. п.6)
13. Nowcast Яндекс.Погоды → мелкий текст "дождь через N мин" в Режиме 1; расчёт стрика привычек поверх `activity_minute` → Режим 7
14. Веб-дашборд (вариант А) поверх готовой SQLite — день, потом неделя, статус online/offline
15. Пройти тест-план (п.9) целиком, до печати корпуса
16. Корпус — печатать только после проверки электроники и прохождения тестов, с вентиляцией под SCD41 и вырезом под экран/энкодер

## 9. Тест-план — прогнать перед печатью корпуса

**Радар (LD2410):**
- Пустая комната → "присутствие" не срабатывает само по себе
- Специально покачать/подвинуть **пустое** кресло — резко и медленно — убедиться, что это НЕ считается "пришёл"
- Сесть неподвижно на 2-3 минуты — "статичное присутствие" держится
- Встать и выйти из зоны видимости — замерить задержку смены состояния
- Вентилятор/шторы рядом — проверка на ложные срабатывания

**Датчик воздуха (SCD41):**
- Сверить с референсным термометром в первый день
- Подышать на датчик — CO2 подскакивает и спадает
- Последить несколько дней за "уходом" нуля CO2 (ASC)

**Сеть/MQTT/heartbeat:**
- Выключить роутер на минуту — Pi сам переподключается
- Убить процесс ПК-агента — heartbeat пропадает и это видно в логах
- Перезагрузить сам Pi — Mosquitto и запись в базу поднимаются сами (автозапуск через systemd)

**Энкодер:**
- Быстро покрутить — нет "прыжков" из-за дребезга
- Короткое/долгое нажатие надёжно различаются на практике (порог 500-800 мс)

**ПК-агент:**
- 5-10 разных программ — категоризация верна на каждой
- 5+ минут без ввода — AFK срабатывает
- Звук отдельно на мониторах и в наушниках
- LibreHardwareMonitor без прав администратора — специально увидеть пустой Режим 5

**Питание/устойчивость (soak-тест):**
- 3-5 дней без вмешательства — утечки памяти/зависания
- Выдернуть питание Pi на 10 секунд — всё поднимается само после перезагрузки (15-30 сек)

**Приложение:**
- Отключить блок от WiFi — приложение честно показывает "офлайн"
- Проверить локальный часовой пояс в недельном отчёте

## 10. Финальный список режимов экрана (крутилка листает эти 7)

| № | Режим | Что показывает | Источник данных |
|---|---|---|---|
| 1 | Часы + погода | Время, дата, погода, CO2/темп мелко; мелким шрифтом — "дождь через N мин", если ожидается в ближайшие 20-30 мин | Pi (NTP, weather API, nowcast, SCD41) |
| 2 | Активность | Игра/код/сёрф, нажатия клавиш/мышь, звук | ПК-агент → MQTT |
| 3 | Меня нет | Сплю/не дома, сколько времени в статусе | LD2410 + эвристика времени суток |
| 4 | Manual Override | Ручной статус, авто-сброс через 4–6 ч | Энкодер |
| 5 | GPU/CPU монитор | Температура/загрузка GPU и CPU, живой график | ПК-агент (LibreHardwareMonitor) |
| 6 | ML-аномалия | Индикатор "необычная сессия" + причина | ПК-агент (IsolationForest) |
| 7 | Стрик привычек | Дней подряд с перерывом каждые 2 часа | Pi (расчёт поверх `activity_minute`) |

Короткое нажатие энкодера в режимах 1–3, 5–7 — листает дальше. Долгое нажатие — вход в Manual Override (режим 4). В самом режиме 4 короткое нажатие — подтверждение выбора.

**Конфликт жестов (не забыть при реализации):** в бэклоге есть идея "долгое нажатие → мини-меню быстрых действий", но этот жест уже занят под Manual Override — понадобится третий жест (двойное нажатие или долгое нажатие именно в Режиме 4).

**Про режим 6:** индикатор должен быть заметен даже мельком (крупная иконка/цвет), а не только текстом.

**Визуальный референс для Режима 5 (GPU/CPU монитор):** ориентир по стилю — панели AIDA64 SensorPanel (круглый стрелочный индикатор загрузки по центру + мелкие цифровые показатели по бокам). Сам AIDA64 не используется технически (у нас данные идут через LibreHardwareMonitor и свой Python-агент), это только референс по компоновке/дизайну, который рисуем сами на Pillow/`luma.lcd`.

## 10.5. Распиновка GPIO (для первого подключения)

**I2C (SCD41, и временно — запасной OLED от Steam-трофея для первого теста):**
| Сигнал | Pin на Pi (физический номер) | GPIO (BCM) |
|---|---|---|
| VCC | Pin 1 (3.3V) | — |
| GND | Pin 9 | — |
| SDA | Pin 3 | GPIO2 |
| SCL | Pin 5 | GPIO3 |

**UART (LD2410):**
| Сигнал | Pin на Pi | GPIO (BCM) |
|---|---|---|
| TX (Pi) → RX (LD2410) | Pin 8 | GPIO14 |
| RX (Pi) ← TX (LD2410) | Pin 10 | GPIO15 |
| VCC / GND | сверить напряжение по маркировке конкретного модуля LD2410 перед подключением |

**Важный нюанс: UART на Pi Zero 2W по умолчанию делит железо с Bluetooth.** Чтобы получить стабильный полноценный UART на GPIO14/15 (а не урезанный mini-UART с плавающей скоростью, привязанной к частоте ядра), нужно явно отключить Bluetooth в конфиге (`dtoverlay=disable-bt`, `enable_uart=1` в `/boot/config.txt`) — иначе связь с LD2410 может периодически "плыть" по скорости.

**Энкодер (KY-040):**
| Сигнал | Pin на Pi | GPIO (BCM) |
|---|---|---|
| CLK | Pin 11 | GPIO17 |
| DT | Pin 13 | GPIO27 |
| SW (кнопка) | Pin 15 | GPIO22 |
| + (VCC) | Pin 17 (3.3V) | — |
| GND | Pin 14 | — |

**Перед подключением чего-либо:** плата Pi Zero 2W обычно приходит без напаянной гребёнки GPIO (это норма, не брак) — нужно сначала напаять стандартную штыревую гребёнку 2×20 (40 pin) на плату, чтобы было куда втыкать провода "мама-...".

## 11. Гифки на экране — теперь просто, без PSRAM-головной боли

У Pi полноценный Linux и нормальная оперативная память — декодирование GIF не требует ничего специального, никакого аналога PSRAM-ограничения ESP32 тут нет.

**Подготовка гифки перед показом:**
1. Обрезать/масштабировать точно под разрешение экрана (например 240×320) — FFmpeg или ImageMagick
2. Библиотека **Pillow** (Python) отлично читает и проигрывает GIF покадрово — можно просто зациклить показ кадров с нужным fps в своём скрипте
3. Хранить гифки прямо файлами на microSD (обычная папка) — никакой возни с LittleFS/C-массивами, как было бы на ESP32

## 12. Бэклог — куда расти дальше ("умные часы на столе")

- **Индикатор статуса на расстоянии** — RGB-подсветка/акцентный светодиод сбоку блока: зелёный = свободен, красный = занят/звонок, синий = отошёл
- ~~Сейчас играет~~ — уже решено: через парсер заголовка активного окна (Режим 2), Yandex Music включён туда же
- **Таймер/Pomodoro** — прогресс-бар на экране, старт/стоп через энкодер
- **Ближайшее событие в календаре** — обратный отсчёт до следующей встречи/пары
- **Мост "важный Telegram-канал → сигнал на этом же блоке"** — вариант с гражданской обороной как ещё один виджет
- **Автояркость экрана** — простой light-sensor (фоторезистор, копейки)
- **Backup RTC на батарейке** (модуль DS3231, ~$1-2) — компенсирует более долгую загрузку Pi после отключения питания, время не теряется совсем
- **Быстрые действия энкодером** — мини-меню: замьютить микрофон на созвоне, щёлкнуть умную розетку
- **Система виджетов как модулей** — конфиг-файл описывает, какие "экраны" включены, без правки кода при добавлении/отключении фичи

**Голосовое управление ("включи/выключи комп", команды по запросу) — отдельный этап после реализации основы:**
- **Включение ПК** — через Wake-on-LAN (`wakeonlan`, magic packet), логика целиком на Pi, т.к. в момент включения игровой ПК ещё выключен. **Важно уточнить заранее:** ПК подключён к роутеру по Ethernet или WiFi — по проводу WoL надёжен, по WiFi многие адаптеры не поддерживают приём пакета в выключенном состоянии; если WiFi не сработает — запасной вариант — реле на Pi, подключённое к разъёму кнопки питания на материнке (эмулирует физическое нажатие)
- **Выключение ПК / прочие команды** — просто ещё один обработчик команд поверх уже работающего MQTT (ПК-агент получает команду, выполняет `shutdown` и т.п.) — архитектурно уже готово, добавляется как ещё один топик
- **Распознавание речи — два уровня по амбициям:**
  - Простой (реалистично на слабом Pi Zero 2W): фиксированный набор ключевых фраз через **Vosk** (лёгкая офлайн-модель), без интернета
  - Продвинутый: свободная речь + LLM для интерпретации — тяжелее, потребует либо облачных API, либо мощного железа локально, Pi Zero 2W для этого недостаточно
- **Нужно будет вернуть микрофон в BOM** — он был сознательно исключён из финальной версии плана (см. историю решений), для голосового управления потребуется добавить его обратно
